01The Big Idea

Before any code makes sense, you need the one distinction the whole app is built around.

A track has a source, and the source decides everything

Every song in Shir is a Track. Every Track carries a MediaSource, which is either .youtube or .localFile. That single enum decides which engine plays it, whether it keeps playing when you lock the phone, whether ads appear, and whether the screen shows a video or album art.

When you get lost in this codebase, come back to this question: which source is this track? The answer explains the behaviour you are looking at.

YouTube — a guest in someone else's house

The app does not own the audio. It asks YouTube's official embedded player to play a video, and YouTube decides what happens — including ads. The app can say play, pause, and seek. That is the whole vocabulary.

Because it is a guest, it plays by house rules: the video stays visible, and playback stops when you leave the app.

Local files — your house, your rules

You imported the file. It sits in the app's own storage. Shir decodes it with AVPlayer, so it can do everything a real music app does: background playback, lock screen controls, AirPlay, and never an ad.

This is where uninterrupted listening comes from. Not from defeating YouTube.

The two-package split

The code is cut in half, and the cut is not arbitrary. Anything that could be tested without a phone was pushed into a separate Swift package so it can be.

HalfWhat lives thereWhy it is separate
ShirKit/ Models, the library store, the playback queue, the YouTube API client Imports no UI framework, so it compiles and tests on a Mac in 17 milliseconds. The tricky logic lives here on purpose.
Shir/ SwiftUI screens, the two engines, keychain, file import Genuinely needs UIKit, AVFoundation and WebKit, so it can only run on a device or simulator.

Why the callbacks point upward

Notice the direction: the view calls down into the coordinator, but the engine reports up through closures (onStateChange, onProgress, onError). The engine knows nothing about the coordinator, and the coordinator knows nothing about SwiftUI. Each layer only depends on the one below it, which is why you can swap the engine without touching a view.

04The Data Model

Five types carry all the state. Four of them are plain values you could print on paper.

Why playlists store IDs, not tracks

A Playlist holds trackIDs, not Track values. So when a track is edited once — a duration filled in, a title corrected — it updates everywhere it appears. Storing copies would leave you with the same song looking different in two playlists.

Why the ID is built from the source

A track's ID is yt:VIDEOID or file:NAME. The same YouTube video added from two different screens produces the same ID, so it lands in the library once instead of twice. Identity comes from where the audio is, not from a random UUID.

Where it is saved

The entire library — every playlist, every saved track — is one JSON file at Documents/library.json. Every edit rewrites the whole file, atomically. That sounds wasteful and is deliberately not: at a few thousand tracks a full re-encode is faster than the bookkeeping a partial-write scheme would need, and it can never leave a half-written file behind after a crash.

05The Two Engines

Same interface, opposite capabilities. The asymmetry is the point, not an oversight.

YouTubePlayerEngine

  • Drives a hidden-from-you WKWebView running YouTube's IFrame player
  • Talks to it by evaluating JavaScript: loadVideoById, playVideo, seekTo
  • Hears back through a JavaScript message bridge posting state and progress
  • Video stays visible at 16:9 in NowPlayingView
  • Ads are whatever YouTube serves — untouched
  • Pauses when the app backgrounds
  • No lock screen controls

LocalAudioEngine

  • Drives an AVPlayer reading a file from the app's own storage
  • Talks to it directly in Swift — no bridge, no JavaScript
  • Hears back through a periodic time observer and end-of-item notifications
  • Shows album art instead of video
  • No ads, ever
  • Keeps playing in the background
  • Full lock screen controls and AirPlay

What lets the coordinator treat them the same

Both conform to one small protocol in Shir/Playback/PlaybackEngine.swift — five methods (load, play, pause, seek, stop) and three callbacks. The coordinator holds both and picks one per track. Adding a third source later, say Apple Music, means writing one more conformance and touching nothing else.

06Code Walkthrough

Six snippets, copied verbatim from the files. Open them in order and you have read the spine of the app.

STEP 1 The fork in the road ShirKit/Models/MediaSource.swift · 8 
public enum MediaSource: Codable, Hashable, Sendable {
    case youtube(videoID: String)
    case localFile(fileName: String)

    /// Whether this source is allowed to keep playing with the screen off.
    ///
    /// Only owned files qualify. Backgrounding the IFrame player to get
    /// audio-only YouTube playback violates the YouTube API Services Terms,
    /// so the coordinator pauses YouTube tracks on resign-active instead.
    public var supportsBackgroundPlayback: Bool {
        switch self {
        case .youtube: return false
        case .localFile: return true
        }
    }
}
Remember: Twelve lines, and they decide the behaviour of the entire app — every asymmetry later in the code traces back to this enum.

STEP 3 How a track finds its engine Shir/Playback/PlaybackCoordinator.swift · 174 
private func engine(for track: Track?) -> PlaybackEngine? {
    guard let track else { return nil }
    switch track.source {
    case .youtube: return youtubeEngine
    case .localFile: return localEngine
    }
}

/// Loads whatever the cursor points at, stopping the other engine so two
/// songs can never play over each other.
private func startCurrentTrack(autoplay: Bool) {
    guard let track = queue.current else { return }
    position = 0
    duration = track.duration ?? 0

    switch track.source {
    case .youtube:
        localEngine.stop()
        youtubeEngine.load(track, autoplay: autoplay)
    case .localFile:
        youtubeEngine.stop()
        localEngine.load(track, autoplay: autoplay)
    }
    updateNowPlayingInfo()
}
Remember: Stopping the other engine before starting one is what stops a YouTube video and an MP3 playing over each other when a queue mixes both sources.
STEP 4 The subtle bug this prevents Shir/Playback/PlaybackCoordinator.swift · 215 
/// Ignores events from the engine that is not currently in charge — a
/// stopping engine emits a final `.idle` that would otherwise clobber the
/// state of the track just started on the other one.
private func isActive(_ engine: PlaybackEngine) -> Bool {
    guard let active = self.engine(for: currentTrack) else { return false }
    return active === engine
}
Remember: Without this guard, switching from a file to a YouTube track would show "paused" a split second after starting, because the dying engine's last gasp arrives after the new engine's first event.
STEP 5 Why Next and end-of-song are different ShirKit/Playback/PlaybackQueue.swift · 90 
/// Advances for a natural end-of-song.
///
/// `.one` repeats the current track, `.all` wraps to the start, `.off`
/// stops at the end and reports nil so the coordinator can halt playback.
@discardableResult
public mutating func advanceAtEndOfTrack() -> Track? {
    guard let currentIndex, !items.isEmpty else { return nil }
    if repeatMode == .one { return items[currentIndex] }
    return step(to: currentIndex + 1, wrapping: repeatMode == .all)
}

/// Advances for an explicit tap on Next.
///
/// Deliberately ignores `.one` — a user pressing Next wants the next song,
/// not the same one again. It still wraps, because reaching the end of a
/// queue via the button feels broken if nothing happens.
@discardableResult
public mutating func skipForward() -> Track? {
    guard let currentIndex, !items.isEmpty else { return nil }
    return step(to: currentIndex + 1, wrapping: true)
}
Remember: Two nearly identical methods exist because a song ending by itself and you pressing Next mean different things — with repeat-one on, only one of them should replay.
STEP 6 Talking to YouTube through JavaScript Shir/Playback/YouTubePlayerEngine.swift · 85 
private func run(_ javaScript: String) {
    guard isPlayerReady else {
        pendingCommands.append(javaScript)
        return
    }
    webView.evaluateJavaScript(javaScript) { [weak self] _, error in
        // Commands fired while the player swaps videos can fail harmlessly;
        // only surface a failure that leaves playback stuck.
        guard let error,
              (error as NSError).code != WKError.javaScriptExceptionOccurred.rawValue
        else { return }
        Task { @MainActor in self?.onError?(error.localizedDescription) }
    }
}
Remember: The IFrame player takes a moment to load, so commands sent too early are queued and replayed on ready — without that buffer, tapping play immediately after launch would silently do nothing.

07Rules That Must Not Break

Each of these looks like a bug if you do not know why it is there. Changing any one of them is what makes the app unshippable or subtly broken.

RULE 1
The YouTube player stays visible
Never give the web view zero size or cover it with artwork. A hidden embedded player is the thing App Store review rejects.
RULE 2
YouTube pauses in the background
The audio background mode exists for imported files only. Do not "fix" YouTube so it plays with the screen off.
RULE 3
Search stays filtered
Requests send videoEmbeddable true and the music category. A test asserts both, because dropping them surfaces videos that legally cannot play here.
RULE 4
The queue never learns about engines
PlaybackQueue is a pure value type. It is only cheap to test because it has no idea audio exists.
RULE 5
Do not name a collection method move
SwiftUI defines its own move on collections. The package's version is moveElements, because two candidates make every call site ambiguous.
RULE 6
Never type into a field without a gate
SwiftUI focuses fields asynchronously, and typeText into an unfocused field is silently dropped. Wait for a real signal, never a sleep.

Where the rules are written down

All six live in CLAUDE.md at the project root, next to the reasoning. That file is the first thing to read before changing anything in here.

08Mental Model — Lock It In

  1. Source decides everything. Ask which MediaSource a track has and you can predict every behaviour: which engine plays it, whether it survives backgrounding, whether ads appear.
  2. The coordinator is the only thing that knows both worlds. Views talk down to it, engines report up to it, and it is the single place where the queue meets audio.
  3. ShirKit is the tested half. If logic can be written without importing UIKit, it belongs there — that is why 51 tests run in 17 milliseconds instead of booting a simulator.
  4. State flows one way. Tap goes down through view to coordinator to engine; change comes back up through closures. No layer reaches sideways or upward.
  5. Uninterrupted listening comes from files you own. The app never fights YouTube for it, because the fight is the part that cannot ship.

When you next change something, ask

  • Does this logic need a phone to run? If not, it belongs in ShirKit with a unit test.
  • Does this change make the YouTube player less visible, or keep it alive in the background? If yes, stop.
  • Am I adding a third audio source? Then conform to PlaybackEngine and add a case to MediaSource — the compiler will point at every place that needs updating.
  • Am I about to write a sleep in a UI test? There is a real signal to wait for instead.
